- [ ] 4.5 Implement `POST /notifications` in this order: key header check, schema validation, key lookup, then template resolution, options contract, and dry-run render, then insert as `pending` and return `202` with UUID and status. Verify tests cover valid email and SMS accepted, no provider called, replay returns the original, replay reflects `sent`, replay of `failed` and `unknown` returns the original, replay after template removal returns the original, different recipient rejected, and unknown template, missing option, undeclared option, mistyped option, and render failure each return `422` and store nothing.

- [ ] 4.7 Ensure rejected requests never record their key and responses expose only the public UUID. Verify a `422` followed by a corrected request with the same key returns `202`, and no response contains the internal integer id.

## 7. Worker and state machine

- [ ] 7.1 Implement the claim query with `FOR UPDATE SKIP LOCKED`: only `pending` rows whose `available_at` has arrived, ordered by `(available_at, id)`, with the returned rows sorted the same way, setting `processing`, incrementing the attempt count, and recording worker id and claim time. Verify tests cover two concurrent sessions never claiming the same row, a future `available_at` skipped, terminal rows never claimed, oldest first with `id` breaking ties, the claim update fields, and the default batch size claiming one row. Each concurrent-claim scenario repeats 20 times within the test.
- [ ] 7.2 Implement outcome writes as single conditional updates requiring status `processing` under the worker's own claim, covering `sent` (with sent time and provider message id), `failed`, back to `pending` with backoff, and `unknown`. Discarded writes are logged with UUID and provider message id and nothing else. Verify tests cover late success after lease expiry but before the reaper runs becoming `sent`, the reaper committing first leaving `unknown` and logging the discard, and a table-driven test over every (starting status, outcome) pair showing only the allowed transitions change the row, a `pending` row cannot jump to a terminal status, and terminal rows never change.
- [ ] 7.3 Implement the reaper that marks `processing` rows whose lease has expired as `unknown` with the lease-expired category, using database time, and sets `updated_at`. Verify tests with controlled `locked_at` show expired rows become `unknown`, `updated_at` changes on reaped rows, unexpired rows are untouched, and reaped rows are never claimed again.
- [ ] 7.4 Implement exponential backoff with full jitter and a cap. Verify unit tests show growth across attempts, the cap enforced, and delays always positive.
- [ ] 7.5 Implement per-notification processing: render at send time without persisting the result, send with the notification UUID as the provider idempotency key, and map outcomes (confirmed to `sent`, transient to `pending` or `failed` once attempts are exhausted, permanent to `failed`, timeout, dropped connection, and unclassifiable to `unknown`). A missing template or render failure becomes `failed` with a render-failure category and no send. Verify tests cover every lifecycle send scenario, the retry reusing the same key, attempts exhausted, no table column holding rendered content, and a log-capture test with a provider that echoes a phone number shows neither that number nor any option value in the logs, while discards still log the notification UUID and provider message id.
- [ ] 7.6 Implement the worker loop and entrypoint (reap, claim a batch, process sequentially, sleep when idle). On SIGTERM or SIGINT it stops claiming and lets the in-flight send finish within the provider deadline. Document running it and its settings in `docs/operations.md`. Verify a loop test with the fake provider drains pending rows to `sent`, a signal test shows no new claims after shutdown and the in-flight row finishing, the process exits at startup when `batch_size × provider_deadline` is not below the lease, and the documented start command runs.
